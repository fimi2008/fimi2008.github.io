# Lionxxw 的个人博客

Astro 7 静态站。文章、日常小记、训练手记和 AI 专栏统一使用 Markdown。

## 本地预览

使用 Node.js 24 和 npm。在仓库根目录运行：

```bash
npm ci
npm run dev
npm run check
```

`npm run check` 会构建并检查站点页面、旧 URL 和段落锚点、内部链接、RSS 与站点地图。

## 写作

在 `src/content/entries/` 新增 Markdown。技术文章用 `kind: article`，路径为 `/articles/<slug>/`。日常小记用 `kind: note`，路径为 `/notes/<slug>/`。两类均填写 `title`、`description`、`date` 和 `path`，日期采用带引号的 `"YYYY-MM-DD"`。设置 `draft: true` 可以保存草稿。正式发文前可用真实随记替换预览小记。

训练手记用 `kind: training`，路径为 `/training/<slug>/`，并填写 `activity`（`strength` 撸铁、`running` 长跑、`cycling` 公路车、`hiking` 徒步）。填写同样的标题、摘要、日期和路径，发布后会出现在首页、归档、训练手记和 RSS。

旧文已经迁为 Markdown，保留原 URL 和段落锚点。《Idea 实战汇总》的六张历史截图原本指向本机，仓库中没有图片文件，正文保留了对应位置和原图编号。

## Codex 定时稿件入口

定时任务在本仓库生成或更新 `src/content/entries/<series>-YYYY-MM-DD.md`。`series` 采用 `skills` 或 `weekly`，日期用北京时间的当期统计截止日期。按相同的截止日期重跑会更新同一文件并沿用同一 URL。收集和对比的窗口统一为北京时间连续七个自然日，`period.start` 是 `period.end` 往前第六天，两端均包含。可直接参照该目录下的两篇样稿：

```yaml
---
title: "标题"
description: "列表页摘要"
date: "2026-11-14"
kind: ai
series: weekly
issue: "2026-11-14"
period:
  start: "2026-11-08"
  end: "2026-11-14"
sources:
  - title: "一手来源名称"
    url: "https://example.org/source"
---
```

- **收集候选**：先用榜单、发布记录找到候选，再核对官方文档、源码或论文。注明查询日期和各指标的统计区间。分别记录 Skills 新增与累计安装、GitHub 新增与累计 Star。注明第三方报告的样本范围及厂商自报数据。来源缺少的数字留空或省略。
- **选题和比较**：每期精选 2–4 个值得拆解的对象，把榜单留作证据。写清它解决的原问题、机制如何工作、替换或缩短了原流程哪一步。至少与一种已有做法或同类工具在同一场景下比较，指出新意是在能力、接口、成本还是流程，说明适用条件和代价。
- **Skills**：给精选项明确的采用判断。涉及同仓库或同服务的多个条目时按工具链解释，避免相加推算用户数。需要安装命令时核对技能来源和 Codex 参数。优先使用来源明确的七天新增数据。若只有累计数，按同一北京时间截点，每隔七天保存一份同源、同口径的累计数据快照，按技能 ID 匹配后相减，并标明「七天累计安装净变化」和两次采样时间。只有一份快照时只展示累计值，按机制和场景做周观察，不发布增量排名。
- **前沿技术**：保留「GitHub 热榜」和「最近 AI 动态」。每条动态标注实际发布日期及一手来源，明确区分已证实的事实、作者判断和待测结论。若引用基准，写清对照对象和测试口径。
- **找实践证据**：在 X、YouTube、Reddit 和技术博客找原始实测、作者演示及复盘。优先使用能看清任务、版本、对照组、次数、失败例和验证过程的材料。区分独立实测和厂商或作者演示，给出原帖、原文或视频时间点。只在实际核对过内容后引用结论。
- **给读者一个验证办法**：用相同输入和验收条件比较新旧方案，先看任务结果，再看耗时、成本、返工和失败后的恢复。对重复任务，纳入现有脚本或手工流程作为对照，并计入建立和维护成本。给出可执行的操作技巧，例如应看哪项输出、何时刷新快照或何时转人工。只有亲自运行的结果才写为实测。正式稿使用默认的 `sample: false`。
- 写稿后运行 `npm ci` 和 `npm run check`，通过后提交。推荐在定时工作流分支创建 PR，或者按已授权的发布策略提交到默认分支。每期 URL 和 RSS 由 Astro 自动生成。

## GitHub Pages 发布

正式切换时在仓库 Settings → Pages 中选择 **GitHub Actions** 作为构建来源。工作流在 PR 和分支推送时构建检查，只有默认分支的推送或手动运行才部署，使用现有 `fimi2008.github.io` 域名。预览阶段在独立本地分支运行。
