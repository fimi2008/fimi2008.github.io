## Agent 怎么找到工具、怎么确认工具做对了

### find-skills 把搜索接进工作流

它的 [SKILL.md](https://raw.githubusercontent.com/vercel-labs/skills/main/skills/find-skills/SKILL.md) 把模糊请求转成查询词，通过 Skills CLI 查候选，再给出用途、来源和安装方式。相对手动翻 GitHub，节省的是发现成本。它提供的是可复用的搜索步骤，搜索范围和排序仍受目录收录与遥测影响。

如果团队已经有固定技术栈和批准过的工具清单，直接查清单更省时间。新任务才更适合交给它探索。例如“小程序截图转为组件”可以分别查截图分析、设计系统和小程序组件，按是否能吃进现有设计 token、是否要求外部账号、输出能否直接验证来筛，流行度只用来发现候选。

### agent-browser 压缩了浏览器观察和操作的往返

传统 Playwright 脚本适合把已知路径固化为可回归的断言。Agent 探索一条未知路径时，需要先看当前页面、选一个操作，再确认页面是否进入预期状态。agent-browser 用简短的可访问性树和元素引用表示当前页面，在同一会话里执行下一步。页面结构变化后重新取快照，避免继续依赖过时的引用。[agent-browser 实现说明](https://github.com/vercel-labs/agent-browser)

[Playwright CLI](https://playwright.dev/agent-cli/snapshots) 也支持可访问性树和元素引用，因此差异要靠任务来测。若项目已有 Playwright 测试和登录状态配置，先复用同一生态。若要接入独立的 Agent 工具链，再比较两者完成同一条公开表单流程所需的快照次数、误点击次数，以及能否用页面结果给出成功证据。Canvas 或语义不完整的控件还需要视觉检查。

## 出片工具优化的是哪一步

HyperFrames 将 HTML、CSS、素材和可定位到具体时刻的动画交给渲染器。视频可以和网页共用一部分表达方式。对于每期只换标题、图片和数字的周报，这把工作从每次重新剪辑变成更新结构化输入、批量渲染。它的优势在于复用和检查中间产物。[HyperFrames](https://github.com/heygen-com/hyperframes)

[Remotion](https://www.remotion.dev/docs/idea) 同样支持程序化视频，用 React 组件按帧描述画面。已有 React 动效和组件库时，迁移到 HyperFrames 的收益需要和重写成本比较。如果现有物料主要是 HTML/CSS，或想让 Agent 直接修改页面式的分镜，HyperFrames 更值得先做一个短模板。先拿两组标题和截图渲染同一个十秒片段，看长标题溢出、素材缺失和重新出片的耗时。

[media-use](https://www.skills.sh/heygen-com/hyperframes/media-use) 把准备好的素材落到项目目录并记录来源，[hyperframes-cli](https://www.skills.sh/heygen-com/hyperframes/hyperframes-cli) 负责预览、检查和渲染。RunComfy 的三个条目把配乐、图生视频和编辑需求路由给不同模型。前者解决**怎样稳定装配已有素材**，后者解决**缺哪类素材时怎样生成**。只做字幕和截图周报，可以先复用手头素材，等具体镜头有需求再引入生成服务。


**本周维护信号。**11 月 14 日的 HyperFrames 提交修正了 `capture` 和 `grade-compare` 对带单位超时值的解析，旧实现可能把 `1s` 当作 1 毫秒。批量跑视频检查时，先固定 CLI 版本，并用一份能成功和一份会超时的样片验证跑批脚本。这次变动修的是工作流可靠性，视频渲染机制本身延续原方案。[GitHub 修复提交](https://github.com/heygen-com/hyperframes/commit/50c21c355aa2e2b5b5e8f203d4c38ce0bde6e6a3)

## 外部设计服务适合什么时候用

[design-mobile-apps](https://www.skills.sh/designed-by-ai/skills/design-mobile-apps) 即使安装到 Codex，生成界面的能力仍来自 Sleek API。它优化的是简报到首份设计、HTML 和预览图的往返。已有小程序组件库时，还得核对导出结果里的布局、交互和样式能否映射到项目的组件。需要尽快上线一个预约网站时，[website-builder](https://www.skills.sh/flowkit-labs/skills/website-builder) 提供的是托管和上线后自动化，评估重点变成账户依赖、后续维护和数据导出。

这期先选一个可量化的试题：用同一任务走两遍浏览器流程，记录完成时间、重试次数和是否拿到了正确的结果。若只是偶尔跑一次，沿用已有工具即可。若每次都让 Agent 花大量往返确认页面状态，再考虑把胜出的工具加进日常工作流。

## 别只对比两个 Agent 工具

11 月 10 日的一份独立对照让 Claude Code 的同一模型分别通过 agent-browser 和 Playwright MCP 检查同一个演示商店。两个方案都找到了作者预设的三处界面问题。该次 agent-browser 用时 **149 秒**，Playwright MCP 用时 **112 秒**。作者还指出，agent-browser 的页面结果较短，但载入使用指南也有开销。每种配置只跑了一次，而且一边是 CLI、一边是 MCP，所以这份观察主要说明应该**把启动、说明文件和实际页面读取都计入成本**。它没有验证 Playwright CLI 的表现。[作者的对照记录](https://www.reddit.com/r/ClaudeCode/comments/1xsfn3i/agent_browser_vs_playwright_mcp_in_claude_code/)

我的选型会多加两组：**同一个 CLI 不加 Skill**，用于判断说明文件有没有帮助，以及**写好的固定脚本**，用于判断是否需要让 Agent 每次决策。固定脚本要把首写和后续维护的工时也记下来。测一次熟悉路径、一次结构变化后的路径，保持模型、输入和验收条件相同。若只能跑少量样本，直接列每次结果。

**上手技巧。**点按钮前可以先用 `agent-browser snapshot -i` 看交互元素，点击之后确认目标状态再取下一步。验证样式时，指定需要检查的视口和元素，并保留截图。Simon Willison 的实践还会把命令和实际输出一起写进记录，便于区分 Agent 说自己完成了什么和页面实际呈现了什么。对本博客，可以先测「从首页进入 AI 观察，打开 Skills 文章，确认十条记录」这一条路径，验收用最终地址、文章标题和表格行数。[agent-browser 命令示例](https://github.com/vercel-labs/agent-browser) · [Willison 的验证方法](https://simonwillison.net/guides/agentic-engineering-patterns/agentic-manual-testing/)

## Codex 安装

在目标项目根目录按需执行一行，末尾加 `-g` 可跨项目使用。

```bash
npx skills add designed-by-ai/skills --skill design-mobile-apps -a codex
npx skills add vercel-labs/skills --skill find-skills -a codex
npx skills add vercel-labs/agent-browser --skill agent-browser -a codex
npx skills add heygen-com/hyperframes --skill hyperframes -a codex
npx skills add flowkit-labs/skills --skill website-builder -a codex
npx skills add heygen-com/hyperframes --skill media-use -a codex
npx skills add heygen-com/hyperframes --skill hyperframes-cli -a codex
```
