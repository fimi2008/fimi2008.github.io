两个版本都回复「报销提交成功」。第一个真的生成了单号，第二个把草稿 ID 当成单号。只给回复文字打分，很容易把两次运行都判成成功。评估应该先写清业务结果，再判断回复是否正确地表达了这个结果。

## 用测试矩阵覆盖关键岔路

| 测试情境 | 要检查的事实 |
| --- | --- |
| 制度有新旧两版 | 引用适用条款，金额口径正确 |
| 缺酒店发票 | 进入等待补件，未触发提交 |
| 用户无权访问他人的单据 | 不返回内容，也不在结果里暴露存在性 |
| 用户重复确认同一草稿 | 业务系统只生成一笔单据，后续返回同一回执 |
| 远端成功后进程中断 | 恢复时核对远端结果，未再次创建单据 |
| 超标并已转人工 | 原任务保留，结果由有权人员审批后再推进 |

组件测试可以用固定输入检查权限、数据转换、金额计算和状态转移。完整运行测试使用可控制的假接口，制造超时、拒绝和迟到回执。运行结束后核对本地状态与假接口收到的副作用次数。少量环境验证再覆盖真实服务行为及合同约定。

## 给模型评估留出波动空间

同一个问题可以有多种正确表述。把必须满足的事实写成断言，语气和解释清晰度另外抽样评审。涉及随机输出时，对代表性任务重复运行，记录成绩的分布和失败类型。比较版本时尽量固定样例、知识快照和工具条件，让变化更容易归因。

一次发布可看任务完成率、错误写入、引用有效性、人工转接和耗时。特定的权限越界或重复写入可以作为阻断条件，其他指标按业务目标判断取舍。把真实故障脱敏整理为回归样例，补足当初没有想到的任务状态。这样一次修复也能增加下一次发布的可检验范围。
