*Agent 系统设计 · 第 03 篇补充阅读*

用户问「杭州的酒店每晚 680 元，可以报销吗？」一次模型请求可能只产生一个动作建议，例如先查出差日期。系统取回日期，把查询结果交还模型。模型接着决定查哪份政策，最后才能给出判断和引用。

这个过程里有两类问题。**模型如何在多步之间接着工作**，属于运行时。**哪版制度适用、用户能看哪些行程、什么情况下允许提交**，属于业务系统。DeepSeek Harness 是一个可以承担第一类工作的开源运行时，简称 `dsh`。具体用哪个模型，由部署所选的模型适配器或接在前面的模型网关决定。 [DeepSeek Harness 官方仓库](https://github.com/deepseek-ai/deepseek-harness)

## 为什么考虑用现成的 Harness

只有一个固定查询动作时，应用可以直接调用模型和接口。复杂度往往从第二次工具调用开始增加。模型给出两次查询时，谁负责执行与配对结果？工具返回错误后，模型该继续还是退出？页面断流时，界面还能从哪里找回执行进度？这些问题会在查政策、核票和解释结果时重复出现。

引入 DeepSeek Harness 的一个可解释的工程理由，是**复用模型执行循环、事件记录和能力装配**，让应用团队集中处理业务规则。这里讨论的是从架构得出的选型理由。是否划算，还要看接入成本和故障测试。DeepSeek Harness 基于 Cordis，由插件提供模型适配、工具、会话日志和执行循环。启动时通过 profile 选择一组组件，并可通过配置覆盖部分实现。 [官方架构](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/architecture.md)

| 运行时问题 | 引擎能接手什么 | 应用仍要做什么 |
| --- | --- | --- |
| 一次任务需要多次模型请求 | 组装本步上下文，调用模型，执行工具，把结果带入下一步 | 定义当前业务目标和结束标准 |
| 工具和模型来源会变 | 通过插件、适配器或 MCP 接入能力，提供执行前后的扩展点 | 决定工具开放给谁，以及用哪个身份、访问哪条记录 |
| 页面需要反馈执行过程 | 产生消息、工具调用和结果等会话事件，经 SDK 提供给宿主 | 过滤可公开事件，映射到用户能理解的进度 |
| 执行器需要单独启动和替换 | SDK 模式提供进程接口和会话操作 | 管理进程生命周期、版本兼容、超时与业务恢复 |

## 跟着引擎跑一轮

在引擎里，**一个 step 包含一次模型请求及该请求产生的工具调用**。如果工具返回后还需要模型处理，一个 turn 可以继续跑下一步。查行程和查制度可以是同一轮里的不同 step，外层报销任务也可能为了等发票或人工复核跨越几天。

引擎的会话日志可以用来重建模型看到的消息。模型发起工具调用、工具结果返回、下一步开始，这些事件也可以用于观察执行过程。但日志出现了一次「调用提交工具」，只能说明执行到了调用环节。业务平台还需要用财务系统的回执判断是否已生成单据。 [官方执行循环与会话日志](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/architecture.md#turn-flow) · [工具执行管线](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/tool-execution-pipeline.md)

## 怎么接入，业务权限仍由应用管

一种接法是用官方 SDK 启动 `dsh` 的 SDK profile，提交会话输入并订阅事件。模型调用走应用管理的模型网关，网关负责模型配置和供应商凭据。业务能力通过 MCP 暴露一组窄接口，宿主收到调用后按当前用户、任务、阶段和资源授权检查。嵌入业务系统时，启动配置可以只装这些能力，以便明确执行器看到的工具面。

举例来说，规划和回复阶段可以请求模型，提交报销只能在执行阶段且用户已确认当前草稿时开放。即便模型在回复阶段再次提出提交，宿主也要拒绝。模型会话结束也不会自动推进 SOP，应用还要校验执行结果，保存新节点或转人工。 [官方 Python SDK](https://github.com/deepseek-ai/deepseek-harness/tree/master/python/sdk) · [第 03 篇的阶段边界案例](/articles/agent-design-03/)

## 我会怎么判断这个选型值不值

我会用同一组差旅样例，比较「应用内直接实现一个循环」和「应用加引擎」两种实现。单次只读问答先看直接实现的维护成本。多个岗位需要动态工具选择、结构化事件和统一执行接口时，再看复用引擎能否减少重复代码。

验证时至少做三次对照：

1. **正常查询**。给定同一行程和政策，检查两种实现取得相同的业务结论、浏览器能看到必要的进度。
2. **异常回调**。让模型在不开放写入的阶段提出提交。检查财务接口收到的写入次数为零。
3. **执行器中断**。在查询途中结束进程，重新启动后检查能否从持久化业务状态继续。若已经发出写入，按回执核对结果。

引擎带来的新增成本包括子进程启动、跨进程调试和版本升级。上游仍处在开发预览阶段，我会固定验证过的版本，并把接入边界放在可替换的适配层里。升级时先跑模型、工具和事件链路的回归用例。这个选型最后要回答的是：**省下的重复运行时代码，是否值得承担一个新增的运行时依赖。** [上游预览状态](https://github.com/deepseek-ai/deepseek-harness#developer-preview)
