一笔报销同时需要财务核对发票和行政确认出差安排。财务与行政维护各自的数据，两个核对步骤也可以独立进行。这时候才有理由考虑把任务分给两个 Agent。

## 先判断复杂度落在哪儿

| 工作方式 | 适用条件 | 带来的成本 |
| --- | --- | --- |
| 单 Agent 调工具 | 目标明确，步骤共享同一套权限和上下文 | 工具契约、状态管理 |
| 按意图路由 | 每个请求主要归一个岗位处理 | 分类误差、转接和澄清 |
| 多 Agent 协作 | 同一目标需要独立权限、并行工作或专业验收 | 派工、同步、结果冲突及失败恢复 |

如果两个查询都能由当前用户授权、结果也可以直接合并，单 Agent 调工具可能足够。独立的审批职责、必须保留隔离的数据或独立的任务完成条件，会使多 Agent 的成本更容易被收益覆盖。

## 用交接产物连接成员

    <li><strong>成员独立执行</strong>按各自权限读取材料并返回证据</li>

    <li><strong>汇总并交付</strong>告知用户结果，保留未解决事项</li>

负责人派工时给出子任务标识、目标、可共享的输入、完成标准和截止时间。行政成员返回「行程已确认」以及可授权引用的记录 ID。财务成员返回发票核验结果和政策出处。负责人拿这些结构化产物作验收，记录异常和未解决事项，必要时发起返工。

成员不需要读完整主会话。每次派工只传足够完成工作的范围，提交产物时保留来源。队列可按成员容量控制并发，任务领取与结果写入带稳定标识。成员超时后可以改派，但负责人需要依靠任务版本判断迟到结果是否仍可接受。

## 定义汇总的完成条件

如果财务通过、行政尚未确认，用户可以看到部分进度，总任务仍保留待办。若两位成员对出差日期有冲突，负责人应核对来源或转人工。引入多 Agent 后，验收可以用一组指标看成本是否合理，例如业务完成率、重复派工次数、端到端耗时和人工返工量。

## 把派工和验收建成两条状态线

我会把总任务、子任务和唤醒事件分别记录。总任务描述用户目标，子任务描述被分派的工作和完成标准，唤醒事件负责通知成员开始执行。收到重复事件时先领取事件，再判断子任务是否仍适用。成员返回的产物进入验收和复核流程，需要返工时创建新的执行尝试。

最终汇总也需要领取。两个成员同时提交结果，可能都观察到「所有工作都结束」。协调器可以用一次条件更新把总任务从运行中切到汇总中，只让成功更新的一方通知负责人。遇到子任务等待用户补充时，总任务可以挂起，已完成产物仍然保留。

例如财务核票与行政查行程可以同时开始，复核必须拿到两份结构化结果之后才能开始。

```text
财务核票 ── 发票校验报告 ──┐
                           ├── 负责人复核 ── 用户答复
行政确认 ── 行程记录引用 ──┘
```

如果行政报告先到，协调器只保存产物并更新进度。如果财务要求补票，可以只暂停依赖它的复核步骤。等用户补交后重新执行有变化的子任务，继续复用仍然有效的行政报告。

我会用两个并行成员同时完成、一个成员重试、一个成员迟到的测试来检验。最终只产生一条有效汇总，并能说明每项判断引用了谁的证据。没有实际独立职责时，我会先使用一个协调器并行调用工具，避免用两个对话会话解决一次可直接计算的合并。

## 并发推演：拿到汇总权之后，进程崩溃怎么办？

财务和行政几乎同时提交结果。两个执行者都看到成员工作已经结束，于是各自尝试把团队任务从「运行中」改成「汇总中」。条件更新可以让其中一方取得汇总权。接下来还有一步：给负责人保存一条待处理的汇总事件。

    <li><strong>窗口二 · 事件已写入</strong><span>A 在启动执行器前崩溃。后台扫描可以找到待处理事件并补派。</span></li>

  <figcaption>条件更新解决谁能发起汇总。持久化事件解决重启后有没有工作可找。</figcaption>
</figure>

一个常见实现是先提交状态，再单独写唤醒事件。对已经落库的待处理事件，可以扫描补派；对已经领取但心跳超时的事件，可以回收后重新领取。这两种恢复都需要数据库中**已有事件**。如果崩溃发生在两个提交之间，扫描事件表无法找回一条从未写入的记录。再次尝试领取也可能被「汇总中」状态挡住。

| 方案 | 能处理什么 | 代价 |
| --- | --- | --- |
| 保持分步提交，补扫「汇总中但缺事件」的总任务 | 能修复已存在的不一致状态 | 要定义扫描时限，并处理扫描与正常写入竞争 |
| 同一事务更新总任务并写入待处理事件 | 提交成功时状态和事件同时可见，失败时同时回滚 | 两者需要共享事务边界，后台仍需补派和去重 |

如果团队状态和事件在同一个数据库里，**我会选同一事务写入**。条件更新成功后，在事务里用「总任务 ID、汇总版本」作为唯一键保存事件，事务提交后再尝试启动负责人。如果事务提交之后、启动之前崩溃，后台仍能找到事件。如果旧数据里已经有「汇总中但缺事件」，可额外做一次受控补扫。

下面是领取和排队的最小实现。这里假定进入汇总后，本版本的成员产物固定，更新产物需要另开汇总版本。

```text
同一事务内：
    有条件更新总任务（状态 = 运行中，版本 = v）
        新状态 = 汇总中
    如果更新行数 = 0：结束，已有执行者或版本已变化
    写入待处理事件（总任务 ID，汇总版本 v，成员产物引用）
        对（总任务 ID，汇总版本）设置唯一约束
事务提交后：
    尝试派发事件。未派发的事件由后台扫描。
```

事件可能被再次投递，负责人也可能在超时后被另一个执行者接手。领取事件可以减少并发，最终发布还要按「总任务 ID、汇总版本」限制可见结果，并校验执行者仍拥有本次领取。旧执行者晚到时，不能覆盖已完成的汇总。这个设计允许计算重做，但同一汇总版本只应向用户发布一份结果。

### 怎么验证这个选择

1. 让两个执行者同时越过「所有成员已结束」的检查，再执行领取。断言同一汇总版本只有一条待处理事件。
2. 在事务提交前注入中断，断言状态和事件都回滚。再在提交后、启动前中断，断言补派可以继续。
3. 模拟同一个事件被重复投递，再让第一次执行的结果迟到。断言只出现一条用户可见的汇总消息，且引用的是当前版本的成员产物。

这道题比「能够并行派几个 Agent」更能检验编排设计。它要求说清状态归谁、后台从哪里恢复，以及哪一层负责阻止重复交付。
