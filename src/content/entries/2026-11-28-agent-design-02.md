周一，用户让助手帮忙报杭州的差旅费。系统核对到一半，发现缺酒店发票。周三，用户上传附件，只说了一句「我补好了」。

接下来要继续哪张报销单？哪些材料已经查过？如果用户同时有一笔上海出差没办完，这句话又该归到哪里？这些问题要靠任务状态回答。

## 拆清四种记录

在一个便于实现的模型里，一条会话可以有多个轮次和任务。一个任务可以经过多个轮次，每次尝试推进任务都可以有独立的执行记录。

| 记录 | 保存什么 | 报销案例 |
| --- | --- | --- |
| 会话 | 参与者、消息和交互上下文 | 用户与差旅助手的聊天 |
| 对话轮次 | 一次用户输入及相应处理结果 | 周三发来的「我补好了」和附件 |
| 业务任务 | 目标、关联对象、当前状态及后续条件 | 杭州差旅报销，等待酒店发票 |
| 执行记录 | 一次尝试的起止时间、动作、结果和错误 | 周三重新校验发票的尝试 |

第一次核对结束时，就可以在任务中保存出差记录 ID、已核对的附件版本、缺失项和等待条件。回复里说“请补酒店发票”只是对用户展示状态。周三的新轮次可以从任务记录里读到同一个条件，并检查新附件是否真的满足它。

## 先关联任务，再解释这条消息

界面允许用户从某个任务点击“补交”时，可以直接带上任务 ID。用户只在聊天里说“补好了”时，系统可以先找**当前用户有权继续、正在等待材料**的任务，再结合城市、日期、附件信息缩小范围。

当前只有一笔匹配任务，而且发票与行程一致，可以继续核验。如果杭州和上海两笔都缺酒店发票，系统可以问「这张发票是杭州 11 月 12 日的，还是上海 11 月 18 日的？」把候选指出来，比让用户从头复述一遍更省事。也可以将附件暂存，等任务确认后再绑定。

有了任务关联，还要判断消息的动作。“这次不报了”属于取消申请。“先报杭州的”可能只是在两个任务中选了一个。系统可以生成一条待校验的动作建议，再按当前状态与权限决定能否推进。

## 把进度和尝试分开保存

同一个任务可以经历多次执行记录。例如发票识别超时，任务仍然可以留在“待核验”，这次尝试则记录为失败。用户重复点了上传，入口可以用请求标识识别同一轮的重送。用户上传了一份更新后的附件，就创建一个新的处理尝试，并重新校验所有依赖票面金额的判断。

这样既能跟用户解释“现在办到哪一步”，也能让维护者回答“上一次为什么失败”。至于一次提交超时后外部系统是否已经创建了单据，需要由工具执行记录和财务接口单独核实，后面的文章会展开。

## 区分三种重复

面试里如果被问到「请求幂等怎么做」，我会先问是哪种重复。浏览器重送同一条消息、用户另起一轮继续同一笔报销、财务接口收到相同的写入，三件事的标识和处理方式不同。

| 重复发生在哪里 | 用什么识别 | 如何处理 |
| --- | --- | --- |
| 客户端重复发送一轮 | 会话、轮次请求 ID，以及请求摘要 | 相同请求已完成就返回保存的回复，同 ID 不同内容视为冲突 |
| 用户补件后继续办理 | 任务 ID 与当前版本 | 开启新的执行尝试，接着处理未完成条件 |
| 提交动作第二次到达 | 逻辑动作键与远端回执 | 成功则返回已有结果，结果未知则先核实 |

我会让同一会话先取得短租约，再领取轮次执行权。进行中的消息重送可以返回「正在处理」或让客户端订阅已有结果。旧进程即使超过租约后才回来，也要携带原领取标识才能尝试写入，存储层据此拒绝过期写入。租约保护写入归属，已经发出去的远端请求还要看工具回执。

验证时把两个相同的轮次请求并发发出，确认持久化只发生一次。然后保留请求 ID 修改附件，确认系统报告冲突。最后换一个轮次 ID 提交补件，确认它能关联原任务，不会另建一张报销单。

## 故障案例：第一条消息发出后断网，刷新页面会创建两次任务吗？

用户首次打开差旅助手，发出「帮我报销杭州的差旅费」。这时客户端还没有会话 ID。服务端完成了首轮处理，但回包丢失。若客户端重送时直接创建一个新会话，即使每个会话内都有轮次去重，这条消息仍会被执行两遍。

### 先解决首轮的会话身份，再做轮次去重

一种办法是先创建正式会话，再发第一条消息。入口更直观，但要处理建会话响应本身丢失的情况。若产品希望发首条消息时才生成会话，我会用**可信的组织与用户身份、首轮请求标识**定位稳定的首轮会话，再在会话内按请求标识保存轮次。客户端则需要在发出请求前保存这个标识，刷新后才能沿用。找到旧会话时，仍要检查它属于当前用户和所选员工。

系统还需要将消息、附件引用及其他会影响执行的输入做成稳定摘要。相同标识配不同摘要，应明确报告冲突。比如用户删除旧附件换了一张票，这是一次新提交。已完成的同摘要请求可以回放原结果；执行中可返回已有进度。如果执行者失联，只能说明本轮未有可返回的结果，接下来根据任务检查点和工具回执判断如何续接。

### 怎么验证不会出现两张单

1. 并发发送两个没有会话 ID 的首轮请求，且请求标识与输入相同。断言只有一个正式会话和一个有效轮次。
2. 隐去第一次返回的响应，刷新后重送原请求。断言复用原会话与业务任务，不再次执行已经完成的轮次。
3. 用同一请求标识替换附件，断言发生冲突。换新标识补件，断言原任务继续，重新校验受到新附件影响的结论。
4. 让原执行者失联、租约到期后又迟到，确认它不能覆盖后续执行写入的状态。若它可能曾发出提交请求，继续按[第 09 篇](/articles/agent-design-09/)的调用回执对账。

这套设计给客户端一个简单但重要的约定：**重送同一动作要保留原标识，用户发起新动作才生成新标识。** 服务端的会话、轮次和业务动作三层状态也因此能各自解释发生了什么。
